Anti-Pattern 5: Fat UI's

Geoffrey Vandiest27 MAY 2010

[Image no longer available]

One of the major flaws in an un-testable design is the very tight coupling between the UI and the actual domain and/or presentation logic. Our typical ASP.NET applications are difficult to test, because much of the logic is contained within the codebehind files, which derive from Web.UI.Page, which needs an HttpContext, which is difficult to mock. Furthermore, the output of the methods in the codebehind is often not easily-testable, because it's a side-effect (such as calling DataBind() on a GridView).

This same problem exists in windows forms: How do you test the logic inside the form when you are unable to control the input & output of the UI? Let’s examine the following code sample.

public partial class LoginForm : Form
{
    const string AUTHNETICATION_FAILED = "Authentication failed!";
    public LoginForm()
    {
        InitializeComponent();
    }

    private void LoginButton_Click(object sender, EventArgs e)
    {
        var membershipService = new MembershipService();

        if (membershipService.Authenticate(
                                 UserNameText.Text,
                                 PasswordText.Text
                                 )
              )
        {
            MainForm form = new MainForm();
            this.Hide();
            form.Show();
        }
        else
        {
            MessageLabel.Text = AUTHNETICATION_FAILED;
        }
    }
}

Apart from being a pretty naïve implementation of a login form, this code is also hard to test. It’s design contains several smells of un-testable design. First of all it instantiates his Services directly, making it impossible to inject his dependencies through test doubles. Another problem is how can we test that; when the authentication was successful, the MainForm is shown?

By applying what we learned earlier we could already make our SUT more testable:

public partial class LoginForm : Form
{
    const string AUTHENTICATION_FAILED = "Authentication failed!";
    private IMembershipService _membershipService;
    private INavigationService _navigationService;

    public LoginForm()
    {
        InitializeComponent();
        _membershipService = new MembershipService();
        _navigationService = new NavigationService(this);
    }

    public LoginForm(
        IMembershipService membershipService,
        INavigationService navigationService
        )  //This constructor is only for testing purposes
    {
        _membershipService = membershipService;
        _navigationService = navigationService;
    }

    public void LoginButton_Click(object sender, EventArgs e)
    {
        if (_membershipService.Authenticate(
            UserNameText.Text,
            PasswordText.Text)
           )
        {
            _navigationService.NavigateTo(new MainForm());
        }
        else
        {
            MessageLabel.Text = AUTHENTICATION_FAILED;
        }
    }
}

public interface INavigationService
{
    void NavigateTo(Form focusForm);
}

public class NavigationService : INavigationService
{
    private Form _form;
    public NavigationService(Form form)
    {
        _form = form;
    }

    public void NavigateTo(Form focusForm)
    {
        _form.Hide();
        focusForm.Show();
    }
}

Here we encapsulated the Navigation logic into a Service and we’ve created a specific constructor that can be used by our tests to inject a test double making possible to write the following test:

[Test]
public void LoginButton_Click_OnSuccessfullLogin_ShouldNavigateToMainForm()
{
    //Arrange
    var mocks = new MockRepository();
    var membershipServiceMock = mocks.StrictMock<IMembershipService>();
    var navigationServiceMock = mocks.StrictMock<INavigationService>();
    var form = new LoginForm(membershipServiceMock,navigationServiceMock);

    Expect.Call(membershipServiceMock.Authenticate(null, null)).Return(true);
    navigationServiceMock.NavigateTo(null);
    LastCall.IgnoreArguments();
    mocks.ReplayAll();

    //Act
    form.LoginButton_Click(null,null);

    //Assert
    mocks.VerifyAll();
}

By applying one of the variants of the MVC pattern namely the PresentationModel we can completely decouple the presentation logic from infrastructure and test it in isolation:

public interface ILoginFormView
{
    string UserName { get; set; }
    string Password { get; set; }
    string Message { get; set; }

    void NavigateTo(Form focusForm);
}

public interface IMembershipService
{
    bool Authenticate(string userName, string password);
}

public class LoginFormPresenter
{
    const string AuthneticationFailedMessage = "Authentication failed!";
    private readonly ILoginFormView _view;
    private readonly IMembershipService _membershipService;

    public LoginFormPresenter(ILoginFormView view, IMembershipService membershipService)
    {
        _view = view;
        _membershipService = membershipService;
    }

    public void LoginButtonClick()
    {

        if (_membershipService.Authenticate(
                    _view.UserName,
                    _view.Password
                    )
            )
        {
            _view.NavigateTo(new MainForm());
        }
        else
        {
            _view.Message = AuthneticationFailedMessage;
        }
    }

}

public partial class LoginForm : Form, ILoginFormView
{
    private LoginFormPresenter _presenter;

    public string UserName
    {
        get
        {
            return UserNameTextBox.Text;
        }
        set
        {
            UserNameTextBox.Text = value;
        }
    }

    public string Password
    {
        get
        {
            return PasswordTextBox.Text;
        }
        set
        {
            PasswordTextBox.Text = value;
        }
    }

    public string Message
    {
        get
        {
            return MessageLabel.Text;
        }
        set
        {
            MessageLabel.Text = value;
        }
    }

    public LoginForm()
    {
        InitializeComponent();
        _presenter = new LoginFormPresenter(this, new MembershipService());
    }

    public void LoginButton_Click(object sender, EventArgs e)
    {
       _presenter.LoginButtonClick();
    }

    public void NavigateTo(Form focussedForm)
    {
        Hide();
        focussedForm.Show();
    }
}

We are now able to test the presentation logic:

[TestFixture]
public class LoginFormPresenterTest
{
    const string UserName = "myUserName";
    const string Password = "myPassword";

    [Test]
    public void LoginButtonClick_AuthenticationSuccess_ViewShouldNavigateToMainForm()
    {
        //Arrange
        var viewMock = CreateLoginFormViewStub();
        var membershipServiceMock = CreateMembershipServiceMock(true);
        var subject = new LoginFormPresenter(viewMock, membershipServiceMock);

        //Act
        subject.LoginButtonClick();

        //Assert
        viewMock.AssertWasCalled(
            s => s.NavigateTo(null),
            options => options.IgnoreArguments()
            );
    }

    [Test]
    public void LoginButtonClick_AuthenticationFailed_ViewMessageIsAuthenticationfailed()
    {
        //Arrange
        var viewMock = CreateLoginFormViewStub();
        var membershipServiceMock = CreateMembershipServiceMock(false);
        var subject = new LoginFormPresenter(
                          viewMock,
                          membershipServiceMock
                          );

        //Act
        subject.LoginButtonClick();

        //Assert
        Assert.AreEqual("Authentication failed!", viewMock.Message);
    }

    private IMembershipService CreateMembershipServiceMock(bool expectedResult)
    {
        var membershipServiceMock = MockRepository.GenerateStub<IMembershipService>();
        membershipServiceMock.Stub(m => m.Authenticate(UserName, Password)).Return(expectedResult);
        return membershipServiceMock;
    }

    private ILoginFormView CreateLoginFormViewStub()
    {
        var viewMock = MockRepository.GenerateStub<ILoginFormView>();
        viewMock.UserName = UserName;
        viewMock.Password = Password;
        return viewMock;
    }
}

When designing UI’s you should make your choice between patterns like MVC/MVP/MVVM and use the most appropriate pattern and/or framework for your project.  With the appropriate design a lot of the presentation logic encapsulated into the UI can be extracted and tested. In this example we extracted all the presentation logic encapsulated in our form and transferred it into a presenter. This presenter is completely decoupled from any infrastructure and we are able to easily obtain 100% test coverage with it. The LoginForm itself remains un-testable but it does not contain any logic anymore. His only purpose is to act as a sort of proxy between the windows forms infrastructure and our presentation logic.
