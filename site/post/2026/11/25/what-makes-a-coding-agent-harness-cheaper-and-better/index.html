What actually makes a coding-agent harness cheaper and better

Geoffrey Vandiest25 NOV 2026

My harness for Claude Code had grown for a year. Investigate, write a spec, review it, plan each slice, build test-first, verify, recap. It worked. It was also expensive, and I no longer knew which parts earned their cost.

A harness is everything around the model: instruction files, skills, hooks, gates, the process the agent must follow. Every piece of it costs tokens. So I asked one simple question: which parts change the result, and which only cost tokens?

To answer it I ran 19 controlled experiments. Each changed one thing and measured the effect on the same task: building one slice of a feature in a Blazor WebAssembly application from an approved spec. Two independent judge agents scored every build on acceptance criteria, on planted bugs caught by the tests, on weak tests and on cost.

The short version

The build cost fell from 5.57 USD to 1.81 USD per slice (−67%). The tests became stronger at the same time: a real page-level integration test, and a mutation score of 100% on the slice's code.

The final run missed my strict quality floor by two minor test gaps, and most conditions were run once. So the last figure is an indication, not a proven mean.

Three things made a measurable difference:

  • removing duplicate work;
  • keeping tool output out of the context;
  • replacing written testing rules by a mechanical check (mutation testing).

Three things did not: shortening or adding instruction text, removing paperwork, and regrouping tool calls. A cheaper model (Sonnet 5.5) held the quality once the mechanical check was in place.

And the results agree with Anthropic's published guidance on almost every point I could test.

The method

Task and baseline

  • Codebase: a Blazor WebAssembly line-of-business application, with unit, UI (bUnit) and integration test projects.
  • Task: build slice 1 of a "CSV export" feature from an approved spec with 11 acceptance criteria (file name with local date, sorted rows across pages, localized headers, quoting, formula-injection guard, a log record without personal data, and so on).
  • Agent: Claude Code, unattended, with a fixed prompt, a fixed tool allow-list and a cap of 300 turns. Opus 5.5 unless stated.
  • Baseline: the harness as it was (kit 2.5.6), built three times: 5.59, 5.64 and 5.48 USD. Mean 5.57 USD, spread ±1.5%.

What I measured

Two judge agents scored each build. Neither had seen the build session.

JudgeWhat it measures
Build judgeAcceptance criteria met (of 11); gate green (0 warnings, all tests, formatting); 2 bugs planted after the build and whether the tests catch them; code quality (0–5)
Coverage judge10 planted bugs (M1–M10) and how many the tests catch; weak tests (cannot fail, or only check a constant or a mock); whether a real integration test exists; line coverage

Cost is the build job's cost in USD. I also recorded turns and the tokens re-read from cache, as a proxy for context size.

Quality floor: 11/11 criteria, 10/10 planted bugs, 0 weak tests, a real integration test.

The loop

Every experiment followed the same cycle.

  1. Propose one improvement, with a reason taken from the previous analysis.
  2. Modify the harness (a new kit version or a setup change) and install it on the fixed baseline commit.
  3. Measure: one unattended build, then both judges.
  4. Analyse: cost, turns and context against the reference; the judges' findings.
  5. Decide: adopt, reject or "not alone". Adoption required at least 5% lower cost with the quality held, or better quality at an accepted cost.
  6. Next: the following proposal comes from what the analysis showed, not from a fixed list.

An adopted change became the new reference for the next experiment.

A defect in my own method

After experiment 10 I found a bug in my runner. It started each session on the repository's default branch and switched to the experiment commit afterwards. Claude Code loads the instruction file, the unscoped rules and the lists of skills and agents at session start. So changes to always-loaded text were never in effect in experiments 1–10.

The consequences: experiment 6 (shorter instruction text) is void, and absolute costs before the fix carry extra text. I fixed the runner so sessions start on the experiment commit, re-measured the reference in isolation at 4.29 USD, and re-tested the instruction-text question in experiments 11–12 and 15.

I report this because it changes how the early numbers must be read, and because it is an easy mistake to make. Start every session on the commit under test.

  • The home-made check failed twice (13, 14) on details of the test runner's output. It blocked correct builds and cost more.
  • Written rules changed nothing (15). The build broke the very rules it had been given.
  • Mutation testing worked (16). Fewest tests of the series, none weak, and an integration test that caught five of the ten planted bugs by itself.
  • Scope matters (17, 18). When the tool mutated whole files, the agent wrote tests for existing code to reach the threshold. In experiment 18, 11 of 12 new view-model tests were off-scope.
  • Limiting the check to changed lines removed that (19). 38 of 38 mutants killed, 122 outside the slice not scored, no off-scope tests, and 44% cheaper than experiment 18 on the same model.

Where the saving came from, roughly:

  • process and output changes on the same model: −26%;
  • the cheaper model: about −44% (experiment 17 against 18);
  • a correctly scoped check: a further −44% (18 against 19).

What made a real difference

  1. The spec. It was the single largest quality factor: 5/11 criteria without it, 10–11/11 with it, whatever the rest of the harness looked like. The spec is where the owner's decisions enter the build.
  2. Removing duplicate work. A separate plan file and a second analysis build repeated what the spec and the gate already did: −14%.
  3. Keeping tool output out of the context. Quiet build and test output: −14% cost, −27% context. The context grows from what the agent reads and runs, not from the instructions.
  4. A mechanical check instead of prose. Mutation testing changed how the agent tested. Seven written rules did not.
  5. Scoping that check to the slice. An unscoped gate creates its own waste.
  6. Model choice, once the gate exists. Sonnet 5.5 met the same floor as Opus 5.5 at 56% of the cost. The gate, not the model, set the quality.

What had no measurable effect

  1. Instruction text, in either direction. −86% of the build skill: no change. Seven new rules: no change.
  2. Paperwork. Dropping the recap file and spec edits: −2%, inside the noise.
  3. Regrouping work. Batching tests, parallel tool calls, many small commands: all more expensive, because each turn re-reads the context and bigger steps grow it.

What made things worse

  1. A sub-agent per command: +54% and more than twice the time.
  2. A home-made verification hook: two versions, two defects, both blocking correct work. A proven tool (Stryker.NET) did the job the first time.
  3. Stale instructions. Old texts left in the project contradicted the new ones. Two builds from the same base differed by 37%.

Anthropic's guidance holds up

I compared my findings with three Anthropic sources: the Claude Code best-practices page, "Harness design for long-running application development" (March 2026) and "Harnessing Claude's intelligence" (April 2026).

On plan mode

Several third-party articles report that Anthropic now puts less weight on plan mode and more on a written spec. I did not find this stated in the Anthropic pages I read, so I treat it as unverified.

My data is consistent with it. Removing the separate planning step saved 14% with no loss. Removing the spec lost half the acceptance criteria. For this kind of work, the spec is the plan.

Limitations

  • One task, one codebase, one slice. A different feature may behave differently.
  • Mostly single runs. The baseline spread was ±1.5% over three runs, but I also saw 37% between two runs with contaminated instructions. Differences under 10% should be read as noise. The larger effects (−14%, −44%, +54%) are outside it.
  • The final run did not fully meet the floor (one criterion partly tested, one weak test). It is the best cost and the best integration test, not a clean win on every line.
  • The judges are models. They were blind to the build session and consistent across runs, but they are not ground truth.
  • Early absolute costs are inflated by the isolation defect. Relative results for skill and setting changes hold.
  • Evaluation is not free. The two judges cost about 4.5 USD per experiment, more than the final build itself.

Keep what decides, drop what only instructs

The harness I ended with is smaller than the one I started with. It produces better-tested code for about a third of the cost.

The pattern behind every gain was the same: keep what carries decisions (the spec) and what can be checked by a machine (the gate, the mutation check); remove what only tells the model how to work.

The practical advice I draw from the measurements:

  1. Invest in the spec; it decides what gets built.
  2. Enforce with a proven tool, not with more text and not with home-made hooks.
  3. Scope every gate to the change under review.
  4. Watch tool output, not instruction length, when the cost is too high.
  5. Measure one change at a time against a fixed task, and start every session on the commit under test.
  6. Re-test the model choice after the gate is in place.
